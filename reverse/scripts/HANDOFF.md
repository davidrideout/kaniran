## The open decision

> "How are we going to generate inputs/outputs to validate that the Rust port matches Lisp?"

Three viable answers; not mutually exclusive.

### Option A — Trace-driven capture (recommended; designed and probed)

Install `sb-int:encapsulate` recorders on each Lisp leaf, run ichiran's existing tests + a Japanese corpus, dump `(fn, prin1(args), prin1(values))` to per-symbol JSONL files. Rust port replays the JSONL as `#[test]`s.

**What's been verified (probe run on `.103` against real ichiran):**

- `sb-int:encapsulate` works on both `defun` and `defgeneric`.
- `prin1-to-string` round-trips cleanly for every leaf type we sampled (chars, strings including Japanese, NIL, keywords, integers, lists, conses).
- `jsown` is already an ichiran dep — JSON output is one library call.
- `ichiran/test:run-all-tests` exists and takes no args — viable primary driver.
- `multiple-value-list` captures values cleanly (some leaves return `(values ...)`).

**What's known to be incomplete:**

- Macros (36 leaves, mostly `dict-grammar.lisp` / `dict-split.lisp` definers) **cannot be captured this way** — they expand at compile time, so there's no runtime function call to hook. Translation strategy is "transcribe the ~600 callsites as Rust data tables." Not blocking for the function leaves.
- Init-time code (anything called during `(asdf:load-system :ichiran)`) fires before hooks can be installed. Workaround: trigger init-equivalent operations after install if they're idempotent; otherwise hand-fixture.
- Coverage gap: niche leaves (specific conjugation handlers, rare counters) won't fire on the 6-test default corpus. **The tracer measures coverage as a byproduct** — files-with-≥1-fixture vs total leaves. Iterate by extending the corpus driver until the gap shrinks.

**Sub-decisions if you go this route:**

| Sub-decision | Options | Default I'd pick |
|---|---|---|
| Where to run capture | Remote `.103` (DB already up), local SBCL + Docker Postgres, no-DB local for pure leaves only | Start local for pure leaves (fast iteration); use `.103` once expanding to dict.lisp |
| Driver | `run-all-tests` only, `+ corpus`, custom workload only | `run-all-tests` + ~5k Tatoeba sentences |
| Output format | JSONL of prin1 strings, native JSON of decoded values, sexp file | JSONL of prin1 strings — round-trip-faithful, no semantic translation needed |
| Dedup | In-memory hash by `(fn, prin1-args)`, accept dupes | In-memory dedup, flag value-disagreement as "non-deterministic" |
| Where fixtures live | `reverse/scripts/fixtures/<pkg>/<sym>.jsonl` | Per-symbol files — Rust modules `include_str!` exactly what they need |
| Self-validation | Skip / Layer-1 self-test only / + Layer-2 replay | All three: install-time checks + replay before declaring fixtures trustworthy |

### Option B — Hand-write fixtures

For each leaf, read it, pick representative inputs in the REPL, save outputs.

- Pros: works for every leaf including macros and init-time code; forces you to understand each function before porting.
- Cons: 271 leaves × maybe 5 cases each = 1300+ hand-written fixtures. Slow. Bias risk — you'll miss inputs the real test suite catches naturally.

Realistic role: complement to (A) for the ~10–15% of leaves the tracer can't cover.

### Option C — Property tests only, no captured fixtures

Express invariants in Rust + `proptest`/`quickcheck`: e.g. `as_hiragana(as_katakana(x)) == x` for hiragana `x`; `mora_length(s) >= 0`; `to_normal_char(c).map(to_normal_char) == to_normal_char(c)`.

- Pros: catches edge cases traces won't (empty strings, surrogate pairs, malformed inputs).
- Cons: invariants are easy to state for `characters.lisp` leaves, hard or impossible for `dict.lisp` leaves that depend on dictionary state. Will not, by itself, prove "Rust port matches Lisp" — only "Rust port satisfies the invariants I happened to think of."

Realistic role: mandatory complement to (A) for the pure-leaf packages, optional for dict-layer.

### My recommendation

**(A) for ~85% of leaves, (B) for the macro / init / unreachable-by-tests stragglers, (C) selectively for the pure leaves where invariants are cheap to write.**

Don't pick (C) alone — it doesn't validate the port, only the invariants.

## What you'd build if you commit to (A)

1. **`query.py emit-targets`** subcommand — emits a Lisp-loadable list of symbols to wrap. Filter by package, leaf-only, status, etc. (≈ 30 lines of Python.)
2. **`reverse/scripts/trace_capture.lisp`** — main tracer. Loads ichiran, reads target list, installs encapsulators, runs driver, writes JSONL, replays for self-validation, uninstalls. (≈ 200 lines of Lisp.)
3. **`reverse/scripts/run_capture.sh`** — scp + ssh wrapper, mirrors `run-remote.sh` pattern. (≈ 30 lines of bash.)
4. **`reverse/scripts/query.py coverage`** subcommand — diffs `fixtures/` against `query.py leaves`, reports uncovered. (≈ 20 lines.)

Total: a long evening's work, assuming nothing surprises us.

## Risks / unknowns to flag before committing

1. **DB requirement on capture host.** `.103` has Postgres configured. If you want capture on a fresh host, expect a few hours of `(ichiran/maintenance:full-init)`. The Docker compose in this repo (`docker-compose.yml`) is designed for this.
2. **Re-entrance.** A traced function called from inside the recorder = infinite loop. Cheap fix is a thread-local guard; build it in from the start, not after the first crash.
3. **Output volume.** Without dedup, expect 100k+ entries per heavily-called leaf (`to-normal-char` likely fires millions of times). With dedup keyed on `(fn, prin1-args)`, expect dozens to low hundreds per leaf. Build dedup in from day one.
4. **Non-determinism.** If a leaf is non-deterministic (gethash on a global initialized in some test order, etc.) the same args produce different values. The tracer should keep all distinct values and flag the symbol — don't silently keep the first one.
5. **prin1 fragility.** Round-trip is faithful for primitive values, but if any leaf returns a CLOS instance or a circular structure, prin1 either fails or produces something unreadable. Gate the recorder on a "primitive args + result?" check; skip/flag non-primitive cases.

## How to resume

### To pick up where this stops

1. Read `CLAUDE.md` for orientation.
2. Read `reverse/scripts/README.md` for tooling specifics.
3. Run `python3 reverse/scripts/build_graph.py && python3 reverse/scripts/query.py stats` — sanity-check that the graph still parses.
4. Skim `reverse/scripts/PORT_PLAN.md` to see the current attack order.
5. Decide: (A), (B), (C), or hybrid? See the table in `## The open decision`.
6. If (A): build the four artifacts listed in `## What you'd build`. Probe artifacts from this session live at `/tmp/probe.lisp` (local) and on `.103` — they validate the design.

### To re-do the underlying introspection (md files)

```sh
bash reverse/scripts/run-remote.sh
```

Pulls fresh md files from `.103`. Then `build_graph.py` + (if you've marked progress) re-mark from a saved `symbols.csv`.

### Probe results (for confidence)

The design has been validated end-to-end on the live ichiran image. See `## Option A` above for the specific facts confirmed. The probe used:

```
ssh david@192.168.1.103
cd /home/david/storage/ichiran
sbcl --non-interactive --load /tmp/probe.lisp
```

(Probe script content is in this session's history; not committed because it's a one-shot artifact, not part of the tooling.)

## Open questions worth answering before more building

1. **Where will the Rust crate live?** Subdirectory of this repo, or separate repo? Affects whether `reverse/scripts/fixtures/` and the Rust test files need to coexist.
2. **What's the target Rust async / DB story?** `sqlx` + `tokio`? `diesel` + sync? Affects how `ichiran/conn` and any DB-touching dict layer functions get re-architected.
3. **JMdict source of truth.** Will the Rust port consume the same Postgres schema ichiran does (so you can share a DB) or a fresh one? If fresh, expect non-trivial schema design work in addition to the function port.
4. **Scope.** Is the goal "port everything" or "port the romanize / segment public API and stub the rest"? The latter is dramatically smaller — maybe 100 functions instead of 700.

These four bullets are the ones most likely to redirect the work. None of them have been decided yet.
